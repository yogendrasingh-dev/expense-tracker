## 1. Phase 0 Objective

Initialize the repo skeleton so every later implementation phase has somewhere to land: package
configuration, TypeScript, linting, formatting, the test runner, Prisma tooling (schema only, no
models), local Postgres via Docker Compose, a CI skeleton, and a Fastify app shaped so it can be
tested via `.inject()`/`.ready()` without binding a real port. No product requirement (FR/BR/SEC/DI)
is implemented in this phase — it is pure infrastructure, per `docs/implementation-plan.md`'s
Phase 0 entry and `architecture.md` §1/§20.

## 2. Approved Scope

- No application code, feature logic, or HTTP routes beyond Fastify's own framework defaults.
- No Prisma models or migrations — schema file limited to `datasource`/`generator` blocks.
- No `@prisma/client` installation (deferred to Phase 1, when models exist to generate a client
  for).
- No `dotenv` — environment loading uses Node's native `--env-file` flag only.
- ESM module system, Vitest, ESLint + Prettier, Husky + lint-staged pre-commit hooks, and a
  persistent local Postgres via Docker Compose (distinct from the ephemeral Testcontainers
  Postgres used by later automated tests).
- One exact development command and one exact production start command — no left-open
  alternatives.
- Node version pinned to 22.x, consistent with CI.

## 10. Deviations from the Approved Plan

1. **`tsconfig.json`'s `rootDir`**: the approved plan specified `"rootDir": "src"`. This was
   changed to `"rootDir": "."` during implementation, because `tsconfig.json`'s `include` also
   covers `tests/**/*`, which lives outside `src/` — `rootDir: src` is invalid/inconsistent once
   sibling directories are included. This is a necessary technical correction, not a scope change.
2. **ESLint type-aware linting scope**: the plan did not specify this detail. `npm run lint`
   initially failed because root-level config files (`eslint.config.js`, `vitest.config.ts`) are
   not covered by `tsconfig.json`'s `include`, and the flat config's type-aware `parserOptions.project`
   setting was originally applied globally. Fixed by scoping that setting to
   `files: ['src/**/*.ts', 'tests/**/*.ts']` only, so root-level `.js`/`.ts` config files are still
   linted (with non-type-aware rules) without breaking the type-aware rules used on application
   code.
3. **Prettier scope**: `npm run format:check` initially flagged `CLAUDE.md` for reformatting.
   Since modifying `CLAUDE.md` or any `docs/*.md` file is out of scope for this phase (and
   generally requires its own review, not an incidental formatter pass), `*.md` and `docs/` were
   added to `.prettierignore`. This was not in the original file list and is recorded here as an
   addition. No documentation file was modified by this phase's tooling.
4. **Husky's default pre-commit content**: `npx husky init` scaffolds `.husky/pre-commit` with a
   default of `npm test`. This was edited to `npx lint-staged`, matching the approved plan's intent
   (pre-commit runs lint-staged, not the full test suite) and `.lintstagedrc.json`'s configuration.
5. **`src/app.ts` formatting**: the file as originally written did not match Prettier's style
   (line-wrapping of a ternary expression); `prettier --write` was run on this single file to
   correct it before `format:check` was confirmed passing.
6. **Live server-boot verification incomplete**: see §9, row 1 — the interactive verification of
   `npm run dev` actually serving a request was interrupted before completion by the user, who
   redirected the session to producing this document instead. This is recorded as an open
   follow-up, not a silently-assumed pass.
7. **Docker Compose was not started**: `docker compose up -d` was never run in this session. The
   file exists and matches the approved shape, but its runtime behavior is unverified.

## 11. Decisions Made During Implementation

Beyond the three tooling decisions already resolved during planning (§6), one additional judgment
call was made while executing, not previously escalated:
- **`npm audit` findings on `prisma`'s transitive dependency**: after installing devDependencies,
  `npm audit` reported 3 high-severity advisories in `deepmerge-ts` (pulled in via `prisma`'s
  `@prisma/config`). Investigation showed the installed `prisma@7.9.1` is already the latest
  available version — there is no newer release that resolves this, and the `npm audit fix
  --force` suggestion would move to an *older* prisma version, which is not a real fix. This is a
  dev-only CLI dependency (not `@prisma/client`, never shipped to production), and the advisory
  (stack exhaustion via recursive object-graph merging) requires attacker-controlled deeply nested
  config input — not a realistic exposure path for local/CI Prisma CLI usage. Decision: proceed
  without forcing a downgrade, and record this as a known limitation (§12) to revisit in Phase 15's
  hardening/dependency-audit pass (`testing-strategy.md` §28) rather than block Phase 0 on it.

## 15. Code Review Pass and Remediations

Per `CLAUDE.md` §17/`development-workflow.md` §13–14, every unit of work gets an AI-assisted
`/code-review` pass before it's considered ready to merge. That pass was run against the Phase 0
working tree (still uncommitted at the time) and found 6 real defects. All 6 were fixed and
re-verified in this same session, before any commit was made.

### Findings and fixes

| # | Finding | Fix applied |
|---|---|---|
| 1 | `npm start` was broken: `tsc` (with `rootDir: "."`, required so `tsconfig.json` could also cover `tests/`) emitted to `dist/src/server.js`, but the `start` script and README referenced `dist/server.js`. Verified by actually building and observing the mismatch. | Added `tsconfig.build.json` — extends the base config, overrides `rootDir: "src"`, includes only `src/**/*` (excludes `tests/`). `build` script changed to `tsc -p tsconfig.build.json`. Re-verified: `dist/server.js` now exists directly, and `node --env-file=.env dist/server.js` boots and serves (see below). |
| 2 | CI never ran `npm run format:check`, contradicting `CLAUDE.md` §8's "enforced ... authoritatively in CI" — a commit that bypassed the local pre-commit hook could merge unformatted code with CI green. | Added a `npm run format:check` step to `.github/workflows/ci.yml`, between `lint` and `typecheck`. |
| 3 | `tests/unit/app.boot.test.ts` was misfiled: it builds a real Fastify instance and awaits `app.ready()`/`app.close()`, which is not a "pure, I/O-free business-rule function" per `CLAUDE.md` §15/`testing-strategy.md` §2's definition of a unit test — filing it under `tests/unit/` sets a bad precedent. | Moved the file to `tests/app.boot.test.ts` (tests root, not under `unit/`); removed the now-empty `tests/unit/` directory; fixed its relative import path accordingly. |
| 4 | `@types/node` was installed at `^26.2.0` — a major version ahead of the pinned Node 22.x runtime (`.nvmrc`/`engines`) — so code could type-check against Node APIs that don't exist at runtime. | Reinstalled with `npm install -D @types/node@22`, resolving to `^22.20.1`, matching the pinned runtime major version. |
| 5 | `buildApp()` called `loadConfig()` internally and `server.ts` also called it independently — duplicated env parsing, and `buildApp()` couldn't be given a different config in a test without mutating `process.env`. | `buildApp()` now accepts an optional `AppConfig` parameter (defaulting to `loadConfig()` if omitted); `server.ts` loads config once and passes it through explicitly. |
| 6 | `parsePort` logic (`Number(process.env.PORT ?? 3000)`) silently produced `0` for an empty-string `PORT` (`??` doesn't catch `''`), causing Fastify to bind a random ephemeral port with no error. | Added a `parsePort()` helper in `src/config/index.ts` that treats an empty/whitespace string the same as unset (defaults to 3000), and throws a clear error for any other non-finite or non-positive value instead of silently proceeding. |
